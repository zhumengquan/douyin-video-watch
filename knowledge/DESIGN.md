# 知识树设计

> 目标：让 agent 看抖音的方式，像人积累经验，而不是每次从零看。
> 新看到的能吸纳，矛盾的能标记，错的能修正 —— **而且修正要留痕，不能悄悄改掉**。

## 为什么不用一个大的 `MEMORY.md`

人的记忆不是一个大文件，是**分层 + 带来源 + 带权重**的：

- 同一个事实听过三次，比听一次可信
- 两个说法打架时，不是覆盖，是**并存并标记冲突**
- 旧的被推翻时，不是删除，是**标记"已废弃"并留下推翻它的理由**

单文件做不到这些，改完就查不出"为什么改"。

## 三层结构

```
knowledge/
├── facts/        事实层：一条一个可验证断言，带来源
├── topics/       主题层：领域内的归纳，引用 facts
├── conflicts/    冲突层：同一主张的多个互斥来源
├── sources/      来源层：每个博主/每条视频的元信息与可信度
└── INDEX.md      总索引：给 agent 加载用的入口
```

### 1. 事实层 `facts/*.yaml`

**一条事实 = 一个可独立验证的断言。** 不写"这个博主讲了很多深蹲技巧"，
写"235kg 深蹲第三次的平均速度是 0.27 m/s"。

字段：

| 字段 | 作用 |
|------|------|
| `id` | 稳定标识，`topic.key` 形式，如 `vbt.squat_velocity_decay` |
| `claim` | 断言本身，一句话 |
| `value` | 结构化值（数字/枚举），方便比对 |
| `unit` | 单位，没有就 null |
| `topic` | 落到哪个主题 |
| `sources` | **来源列表**，每个带 `aweme_id` / `t`（画面时间戳）/ `kind` |
| `confidence` | 0–1，随来源数量和来源可信度变化 |
| `status` | `active` / `superseded` / `disputed` |
| `supersedes` | 如果它推翻了旧事实，写旧 id |
| `note` | 需要说明的边界条件 |

**关键：`sources` 是复数。** 多来源印证 → confidence 升；
来源互斥 → status 变 `disputed`，同时开一个 conflicts 条目。

**关键：不删事实。** 被推翻就 `status: superseded` + `superseded_by`，
原文留着。这样才查得出一条知识是怎么演化的。

### 2. 主题层 `topics/*.md`

一个主题 = 一个领域（如 `vbt` 举重速度训练、`home_cooking` 家常菜）。
用 Markdown 写，因为要能读给人看。结构：

```markdown
# 主题：xxx

## 核心结论
（引用 facts 里最稳的几条，带 confidence）

## 已知冲突
（链到 conflicts/）

## 边界与失效条件
（这些结论在什么情况下不成立）

## 未解决的问题
（看了但没看懂的，留给以后）
```

主题层**不放新事实**，只做归纳和索引。避免同一个结论两处维护、然后不一致。

### 3. 冲突层 `conflicts/*.yaml`

两个来源说不一样的事时，**不是选一个信**，而是记下来：

| 字段 | 作用 |
|------|------|
| `id` | 冲突标识 |
| `question` | 争的是什么 |
| `positions` | 每个立场 + 支持它的 sources |
| `resolution` | `unresolved` / `resolved_by:<fact_id>` / `unresolvable` |
| `why` | 为什么这么判，或者为什么判不了 |

`unresolvable` 是**合法的长期状态**。比如"简介说判无效、画面显示成功"，
两条证据都在，就是无法调和，那就一直挂着，别硬编一个答案。

### 4. 来源层 `sources/*.yaml`

每个博主一个文件，记：

- `sec_uid`、昵称、粉丝数
- `reliability`：0–1，**根据"它说的和画面是否一致"累计调整**
- `observed`：看过哪几条、各自的发现
- `patterns`：反复出现的话术/套路（比如"标题永远说丝滑稳定，但数据不支持"）

`reliability` 是最有价值的部分：**它让"这个号的话要不要信"变成一个有据可查的数，
而不是印象。**

### 5. 索引 `INDEX.md`

给 agent 启动时读的极简入口：有哪些主题、哪些高风险冲突、哪些来源不可信。
控制在 100 行内，不要变成第二个大文件。

## 三个动作的定义（这是整套东西的核心）

### 吸纳 `absorb`

看到新东西，已有知识里没有 → 建一条 fact，`sources` 只写当前这条，
confidence 按来源可信度给初值（单来源默认 0.5）。

**如果新事实和已有事实说的是同一件事、值也差不多** → 不给新 fact，
而是**往已有 fact 的 `sources` 追加**，并**提高 confidence**。这就是"学过三次更可信"。

### 修正 `revise`

新证据推翻了旧结论 → 
1. 旧 fact 改 `status: superseded`，加 `superseded_by`
2. 建一条新 fact，加 `supersedes`
3. `note` 里写清"原来以为 X，实际是 Y，因为 Z"

**绝不直接覆盖旧值。** 覆盖之后就说不清"我为什么改主意"。

### 冲突 `conflict`

两个来源都能拿出证据、但互相矛盾 →
1. 两条 fact 都保留，`status: disputed`
2. 开一个 conflicts 条目，两边证据都列
3. `resolution: unresolved`，除非有第三方证据能裁决

**不要为了"知识库干净"去强行和解。** 挂着未解决，比编一个假答案好。

## 给 agent 的操作顺序

看完一条视频后：

1. 提取候选断言（只取画面里能确认的 + 标清哪些只是创作者说的）
2. 对每条候选，去 `facts/` 里找同 `id` 或同 `topic` + 近义的
3. 分三种情况：不存在 → `absorb`；存在且一致 → 追加来源；存在且不一致 → `revise` 或 `conflict`
4. 更新 `sources/<作者>.yaml` 的 `observed` 和 `reliability`
5. 更新 `topics/<主题>.md`
6. 更新 `INDEX.md`

**每一步都要能回答"这条知识是怎么来的"**，否则宁可不写。
